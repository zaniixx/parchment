# Parchment

A personal blog: posts, short notes, and photo galleries, all built with
[Eleventy](https://www.11ty.dev/), hand-written CSS/JS, and no client-side
framework. Content is edited through [Decap CMS](https://decapcms.org/) and
committed straight into this repo — there's no database.

This document is my own record of why the project is put together the way
it is, and the problems I actually ran into building it.

## Why these choices

### Eleventy, no framework
I wanted a blog, not an app. There's no client state that needs a
framework's help — every page is static HTML, so I picked a static site
generator over React/Next/Astro-with-islands and kept the JavaScript to a
handful of small, dependency-free scripts (theme toggle, mobile nav,
scroll reveal, the search popup). Less to build, less to ship, less that
can break.

### One feed, three content types, tags as the taxonomy
Posts, notes, and galleries all live in `src/content/` as separate
directories, but they share one thing: a `.11tydata.js` file per directory
that tags every item with its type (`writing` + `posts`/`notes`/
`galleries`). That base tag, plus whatever tags I add per-item, is what
Eleventy's automatic tag collections turn into pages — `/posts/`,
`/meta/`, `/writing/`, and so on are all just tag pages generated by one
template (`src/tags.njk`). I didn't build a separate "categories" system
because tags already do the job; adding a new tag automatically gets you
a new index page for free.

Notes deliberately have no title field — they're meant to be short,
timestamped thoughts, not mini-posts. `partials/feed-item.njk` renders
them differently (just the body) to keep that distinction visible in the
feed instead of forcing every content type into the same shape.

### Drafts that actually stay hidden
Decap's boolean widget defaults new posts to `draft: true`, and I wanted
that to mean "not on the live site" without needing a separate staging
environment. `src/_11ty/computed-permalink.mjs` checks
`ELEVENTY_ENV === "production"` and, when a post is a draft in that mode,
sets `permalink: false` **and** `eleventyExcludeFromCollections: true`.
Both matter — `permalink: false` alone stops the page from being written,
but it doesn't stop the draft from showing up in the homepage feed, tag
pages, or the RSS feed with a link to a page that doesn't exist. Locally
(`npm start`), drafts still render, so I can preview them before
publishing.

### CSS inlined at build time
There's no separate stylesheet request — `eleventy.config.js` has an
`inlineAsset` shortcode that reads `style.css` with `readFileSync` and
drops it straight into a `<style>` tag in the `<head>`. One less
round-trip, and it fits the site's whole "keep it light" ethos.

### A page-weight counter, on purpose
The colophon page reports the byte weight of every page on the site,
computed at build time. That needs the build to run twice
(`scripts/build.mjs`): pass one renders the site so
`compute-weights.mjs` can measure the real HTML output, then pass two
re-renders so the templates can read the now-populated `weights.json`.
It's a bit of extra build complexity in exchange for being able to hold
myself honest about page bloat instead of just asserting the site is
fast.

### No database — git as the backend
Decap CMS commits Markdown files directly to this GitHub repo through
its GitHub backend. That means publishing a post *is* a git commit —
no CMS database, no separate content API, and the full history of every
edit is just `git log`.

### A hand-rolled OAuth proxy on Cloudflare Workers
Decap's GitHub backend needs an OAuth proxy to exchange the GitHub login
for a token — it can't talk to GitHub's OAuth endpoints directly from the
browser. Netlify normally provides this for free if you host on Netlify,
but this site is on GitHub Pages, so I wrote a small proxy
(`decap-oauth-proxy`) and deployed it as a Cloudflare Worker instead of
standing up a server somewhere: it's a few dozen lines of code, Workers'
free tier is enough for a personal blog's login traffic, and it means one
more static, serverless piece instead of something I have to keep
running.

### GitHub Pages + Actions for hosting
The site builds and deploys via a GitHub Actions workflow on every push
to `main`. Since it's a project page (`zaniixx.github.io/parchment/`,
not a root user page), the Eleventy config sets `pathPrefix: "/parchment/"`
so every internal link, asset path, and the generated search index all
resolve correctly under that subpath.

### Search: a build-time JSON index, no library
Client-side search on a static site doesn't need a search server — it
needs an index. `search-index.njk` follows the same pattern the existing
`sitemap.njk` already used: loop over `collections.writing` at build
time and emit one JSON file. The search box fetches that file lazily
(only once the user opens it) and filters it with plain string matching
in `main.js` — no Lunr, no Fuse.js. For a site with a few dozen posts,
a dependency for fuzzy search felt like solving a problem I don't have
yet; a substring match is `indexOf` and a `.filter()`. Typing `#tag`
switches the same input from matching titles/excerpts to matching the
item's tags, so the "search" and "browse by tag" mental models share one
box.

The search UI itself went through a redesign: it started as an
always-visible input sitting in the header, but that didn't fit the
site's look, so it's now a small icon button that opens a compact popup
anchored underneath it — closed by `Escape` or a click outside.

## Challenges I ran into

**Ran the host machine's C: drive completely out of disk space.**
Installing the OAuth proxy's dependencies (`wrangler`, `@cloudflare/workers-types`)
hit `ENOSPC` with the drive at 0 bytes free. The fix wasn't cleaning up
the OAuth proxy — it was moving that whole project to the D: drive, which
had 360GB free, and pointing npm's cache there too so the install
wouldn't immediately hit the same wall again.

**A dependency version mismatch on the very next install.**
Once disk space wasn't the problem, `npm install` failed again — this
time on a real `ERESOLVE` conflict: `wrangler@4.125.0` wanted
`@cloudflare/workers-types@^5.x` as a peer dependency, but my
`package.json` still pinned `^4.20250101.0`. Bumping the pin to `^5.0.0`
fixed it cleanly.

**GitHub silently rejected the OAuth callback.**
After deploying the proxy and wiring up a GitHub OAuth App, login failed
with "the redirect_uri is not associated with this application." The
proxy was sending GitHub a callback URL with `?provider=github` appended
to it, but GitHub validates the `redirect_uri` as an exact match against
what's registered — the query string was enough to break the match. The
fix was to stop appending anything to the callback URL and just use the
plain `/callback` path everywhere it's referenced (both the authorize
request and the token exchange have to agree on it).

**A published post that "didn't show up," but was working as designed.**
The first real test of the CMS → the post I published never appeared on
the live site, and my first assumption was a broken deploy pipeline.
The actual cause was the `draft: true` default on Decap's boolean
widget — I'd saved the post without unchecking it, and the site was
correctly hiding it in production. Nothing was broken; I'd just left a
form field at its default.

**A search index that would have 404'd every result.**
Before shipping the search feature, I noticed the generated
`search-index.json` had URLs like `/posts/test-post/` instead of
`/parchment/posts/test-post/`. The JSON is built by a plain JavaScript
filter function, not a Nunjucks template, so it never went through the
`| url` filter that applies the site's path prefix everywhere else.
Caught it by actually reading the generated JSON before deploying,
rather than assuming the build succeeding meant it was correct.

**A CSS override that didn't override anything.**
The mobile layout for the search box (before the icon redesign) refused
to take the full width of its row no matter what I set on it — turned
out the responsive `@media` rule was positioned *earlier* in the
stylesheet than the plain, unconditional rule it was supposed to
override. Equal specificity, later source order wins, media query or
not. Moving the responsive rule to after the base rule fixed it.

**CSS edits not showing up without a manual restart.**
Because the stylesheet is inlined via a build-time `readFileSync` call
rather than referenced as its own file, Eleventy's dev-server watcher
doesn't know it's a dependency of every page. Editing `style.css` during
`npm start` needed a full server restart to actually see the change,
instead of the usual live-reload.

**Verifying "it works" meant actually opening a browser.**
More than once, code that looked correct on paper (or passed a build)
didn't work in practice until it was clicked through in a real browser —
the path-prefix bug and the CSS cascade bug were both things a build
success would have hidden.
